## Design notes

- Authority never comes from the model. A tool runs with the principal
  that called it, the catalog only shows what that principal may call,
  and every call re-checks scope and the strict schema; an argument the
  schema does not name refuses the call rather than being stripped, so
  `approvalMode: unattended`, a caller identity or a widened slippage are
  errors the run records, not inputs the platform reads.
- The fixture adapter is deliberately naive: it does what it is told by
  whatever it reads. That is the point of the adversarial tests: the
  refusals must come from the tool layer, and they do, whether the
  instruction arrives in a retrieved page, a tool output or the question.
- Proposals are requests for review, never orders. Opening is a user
  session's act, whatever an agent's scopes; an investment proposal opens
  into an ordinary `DRAFT` intent that still needs a plan, an
  acknowledgement bound to the plan hash and the wallet's signature, so
  the review path of B09 to B11 is unchanged and unbypassable.
- Provenance is digests and identifiers by construction: the input
  summary allowlists identifier, enumeration and amount fields, questions
  and texts are hashed, tool outputs are hashed and sized, and the
  validated answer is the only model text kept.
- Events are facts in sequence, not deliveries: they are recorded in the
  transaction that changes the state they describe where one exists
  (`execution.pending`), read by owner and paired device, never by an
  agent or operator, and delivery (outbox, channels, preferences) is B16.
- No domain rule was duplicated: the tools call `planning`, `policy`,
  `strategies`, `research`, `analytics`, `accounting` and `catalog`
  methods, two of which (`indicative`, `quoteIndicative`) were added as
  read-only entry points to logic the planner already had.

The first full `pnpm verify` run failed one test: the execution test's
new events read answered `INTERNAL` because the harness wired the agent
service (which serves the event log) only when a companion adapter was
requested, and the silent test logger hid the cause until
`MARKOV_TEST_LOG_ERRORS=1` (a new harness switch) printed it. Every
harness app now carries the research and agent services, with the model
adapter only when a test asks for one, and the execution test asserts the
status of that read. The proposals list assertion then tripped on a tie:
two proposals created at the same frozen-clock instant have no "newest",
so the test compares them as a set (the store orders by creation time and
then id, so a page is stable). The agents API test had failed four times
while it was being written, each a fact about the API and not a defect: the investment proposal was
policy-denied for issuer concentration because the exposure declared no
cash, so the tool now declares the cash the wallet keeps after the plan
exactly as the planner does; the FXBIO fixture leg is stale by design and
the same `REFERENCE_STALE` rule that gates planning refused it, so the
proposals in the test use a plannable pair (FXAERO, XSFXA) while the
stale basket keeps proving the `data.stale` event; the frozen legs of a
version have no contractual order, so the rebalance rows are looked up by
symbol; and the owner's run list holds the account's runs, the reader
credential's included (five, not four). The tests then proved:

- the catalog is filtered per principal and every tool refuses an
  argument its schema does not name (`limit: 999`, `ownerUserId`,
  `approvalMode`), a scope the credential lacks (`thesis.draft` for a
  reader, everything for another person's agent) and a resource of another
  account (wallet, decision, instance, receipt: `NOT_FOUND`);
- `instruments.facts` and `exposures.compare` say when a price is stale,
  `plan.indicative` conserves the budget, `quote.request` refuses a
  slippage above the owner's limit before the venue is asked,
  `policy.explain` explains a denial with a remedy and an allowance as
  "not an approval";
- the malicious retrieved document: the fixture model follows all three
  instructions and the tool layer refuses them (`NOT_FOUND` for a tool
  that does not exist, `VALIDATION_FAILED` twice), the owner's limits are
  unchanged, no proposal exists, the answer reports the refusals and
  claims nothing, and the provenance contains no page text;
- the model asking for escalation itself (unattended approval, another
  person's wallet, a `proposal.open` tool): refused and recorded, while
  its one legitimate `instruments.search` call is answered and cited;
- a `research:read` credential's run cannot propose; a hostile adapter
  that never stops calling tools fails its run with `BUDGET_EXHAUSTED`
  refusals in its provenance; runs past the daily cost cap answer
  `BUDGET_EXHAUSTED`;
- the review boundary: an agent creates an investment proposal, cannot
  open or dismiss it, another person cannot see it, the owner opens it
  into a `DRAFT` intent idempotently, a dismissed or expired proposal
  cannot be opened; a rebalance proposal carries the instance allocation
  with drift against the creator's threshold, is not executable and
  records `data.stale` for the stale leg;
- events: `proposal.created` and `review.required` per proposal, paging
  by `after` and `limit`, the owner and a paired device read them, an
  agent and another person do not, revoking the device records
  `device.revoked` and the revoked device is refused; the execution test
  sees `review.required`, `execution.pending` and `execution.finalized`
  for a finalized buy.

## Unresolved risks and dependencies

- A hosted model provider (OD-19): terms, retention, the exact data sent
  and the cost rate the budgets are measured in must be recorded in
  `docs/markov/agent-permissions.md` before one is configured; the
  adversarial fixture page should then be re-run against it.
- Cost accounting is in micros of a billing currency the fixture charges
  one per token; a real provider's tokenisation and pricing decide the
  daily cap's meaning.
- Companion runs execute inline in the API request with a 60 s deadline;
  a queue and a worker are needed before long runs or many concurrent
  users (Temporal is available).
- Events are recorded, not delivered; the outbox, channels and
  preferences arrive with B16, as do reviewed rebalance intents behind a
  `rebalance` proposal (today it places nothing).
- Devices read the event log with `status:read`; the device gateway,
  firmware and motion are out of scope for the backend and remain so.
- The web companion panel and typed action proposals are F14.
