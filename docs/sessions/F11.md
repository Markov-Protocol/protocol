## Design notes

- Attribution is the backend's decision (`attributeIntent`): one active
  instance per strategy and wallet, ambiguity stays unassigned. The app's
  only contribution is to make that instance exist before the investment
  is planned, from the owner's review; it never reassigns a lot.
- The instance's actual allocation is a share of the instance's own valued
  holdings, and targets are compared among the invested legs because the
  recipe's cash share is held in the wallet and is not attributed. The
  screen says so rather than inventing a cash position for the instance.
- Sums are exact: values are parsed at the API's scale into BigInt and
  added; a single unknown addend makes the sum unknown and the screen
  says which assets are unpriced. Display rounding (two digits, half-up)
  happens once, and the exact string stays one disclosure away.
- A quantity is shown as tokens only with the multiplier the API reports
  for the point; otherwise base units are shown and labelled. A value is
  the API's position value and is never multiplied again.
- A return that is not reported shows the API's reasons; a deposit is a
  flow (`netFlows`), never return; the model series is labelled as not
  anyone's account. The period control is shared by both panels so a
  comparison is always over the same window.
- Downloads are the API's answers serialised as received (`Blob` and an
  anchor); nothing is uploaded and a refused export saves nothing.

## Verification

The browser journey took four rounds to pass, each for something the real
system did that the first draft had not modelled: a `<summary>` is not a
button for Playwright; the first reconciliation of a freshly funded wallet
finds two inflows nobody explained (the lamports for fees and the
stablecoin funding), so the journey explains them as deposits before the
checkpoint can match; the funding control that simulates the later
deposit also tops the lamports back up, so it flags one or two inflows
and the journey explains every one; and two disclosures match the same
text once the model panel is on the page. Nothing in the app changed for
those; the screens showed exactly what the API recorded. The jsdom suite
caught two of my own mistakes before that: the instance heading is the
instance's label until the recipe loads (the tests now wait for the
title), and the formatter prints `Sep 24, 2026, 1:00 PM UTC` where a
test expected an ISO string. The F09 and F10 evidence screenshots that
the regression runs re-captured were restored so this commit's evidence
is F11's own.

Every figure the tests assert was computed by hand from the fixture
numbers before the model existed: 150,000,000 base units at a ×2
multiplier are 300 tokens, worth 3,000 at 10 and never 6,000; 1,800 +
3,000 + 900 is 5,700; a 60/30/10 recipe invested 1,800 and 3,000 has
targets of 66.67 % and 33.33 % among its invested legs, actual shares of
37.50 % and 62.50 %, and drifts of −29.17 and +29.17 points. The full
gate then ran green with the site included.

## Provider verification status

No provider is involved: the reference prices are the fixture feeds'
values recorded at ingestion and one synthetic operator SOL observation
for the run; the chain is the fixture RPC; the wallet is the fixture
wallet. Every figure the screens show is `FIXTURE_VERIFIED` in that sense
and nothing is a live valuation. No funds were spent, nothing was
published, no mandate was created and no message was sent.

## Unresolved risks and dependencies

- Live reference prices (OD-23) decide whether a production portfolio is
  ever "complete"; until they exist the screens will say "Incomplete" and
  name the unpriced assets, which is the intended behaviour.
- Instance labels: instances carry no title, so the wallet overview names
  one by its strategy id and pinned version until the instance page loads
  the recipe. A label on creation (`label`) is supported by the API and
  could be set from the review in a later session.
- The instance page reads the recipe from the owner route first and falls
  back to the public version on 404; a private strategy of another owner
  followed through an instance would show "The recipe could not be read"
  with the API's answer, which cannot happen through the app today.
- Accepting a proposed version (`POST /v1/me/instances/{id}/pin`) is not
  in the app (the notice says a newer version awaits acceptance); F12
  brings the diff and the explicit acceptance.
