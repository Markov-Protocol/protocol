## Provider verification status

No provider is involved. Registration is IMPLEMENTED and
FIXTURE_VERIFIED: the program's rules run in the fixture ledger of
`scripts/dev/fixture-rpc.mjs` under the development placeholder program
id, the fixture wallet signs real legacy wire bytes, and the API derives
every state from what that ledger reports. No program is deployed, no
validator or live cluster was used, no funds moved and no message was
sent. Fees shown are the API's estimate (rent-exempt minimum plus the
base fee). Follows are database bookkeeping only.

## Unresolved risks and dependencies

- Everything on chain is a fixture: a deployed devnet program, a
  validator run, a reproducible build and an independent review (OD-09),
  and the upgrade-authority process (OD-10) remain release gates before
  any registration outside local fixtures.
- Real browser wallets are not verified: the fixture wallet signs
  whatever it is given, so wallet-side simulation warnings, versioned
  transaction handling and rejection flows of real wallets are untested.
- The status-change read answers only the newest deprecation or
  reactivation; a person who prepared one, let it expire and prepared
  another sees the newest, which is what the chain will decide on.
- Public page titles are read server-side from the API with a two-second
  timeout; a slow API yields the generic title, never a stale private
  one.
- Moderation (OD-20) has no route: a withheld version disappears from the
  public pages and from follows, but nobody can withhold one yet.
- Follows are not shown anywhere but the public page's button and count;
  a follower's list on the Build page and update notifications arrive
  with the discovery and companion sessions (B14/F12, F14).
