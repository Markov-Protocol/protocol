## Delivered

- Whole-basket composition at plan time. `VenueAdapter.compose` (every leg
  in one transaction: compute budget, idempotent account creations first,
  swaps in leg order from the owner's one stablecoin account) is
  implemented by the fixture venue and null for the configured-URL venue.
  The planning service composes a multi-constituent basket after the
  quotes and policy decisions, measures the bytes against the packet limit
  (1232 bytes) and simulates them on the node; `assemblePlan` makes the plan
  `atomic` only when the composition fits and passed (`grouping.reason:
  composition_fits`, `grouping.composition {sizeBytes, maxBytes, legs}`,
  `validity.simulation`) and `staged` with the reason otherwise
  (`composition_too_large`, `composition_simulation_failed`,
  `composition_unavailable`); the reason is part of the hashed plan and the
  staged note says what is checked again before each later transaction.
  Fixture venue test controls `composeMaxLegs` and `quoteShiftBps`;
  `EXECUTION_VENUE_FIXTURE_COMPOSE_MAX_LEGS` (fixture provider only, refused
  otherwise) keeps a staged basket for the planning test and the web
  journeys.
- Multi-leg execution rules (`@markov/execution`, pure): the validator takes
  the batch's legs and requires exactly one swap per leg within its bounds
  (`ROUTE_MISSING`, `ROUTE_DUPLICATED`, `MINT_MISMATCH` per leg), account
  creations and writable accounts limited to the owner and the owner's
  token accounts of those legs, rent per account created; effects carry
  the total input and one entry per leg with its mints, exact input,
  minimum output and token accounts. Fills are read per leg (validated
  exact input per swap, outputs per mint, the observed total must equal
  the sum or the fill is uncertain; fee and lamports on the first leg's
  fill). The lifecycle knows the batch and the batch count: a non-final
  transaction that finalizes returns the intent to `AUTHORIZED` for the
  next signature; a failure or an expiry after an earlier fill ends
  `PARTIALLY_COMPLETED` (`execution.partial`).
- Contracts: grouping reasons and composition evidence, transaction effects
  per leg, batch states and `ExecutionStatus.batches`, refusal codes
  `LEG_TERMS_CHANGED`, `BATCH_NOT_READY`, `PLAN_COMPLETED`, the
  `execution.partial` outbox kind, `Intent.continuation` and
  `continuedByIntentId`, `IntentCreateRequest.continuationOfIntentId`
  (baskets only); staged transitions in `INTENT_TRANSITIONS`
  (`AUTHORIZED` reachable again from `SUBMITTED`, `CONFIRMED` and
  `UNKNOWN…`; `PARTIALLY_COMPLETED` terminal).
- Execution service: builds the plan's next transaction (the first batch
  whose legs have not all filled; `PLAN_COMPLETED` when none is left), one
  composed transaction for an atomic plan and one leg per transaction for
  a staged one; the second and later transactions of a staged plan are
  quoted again, checked as at plan time and against the approved bounds,
  the fresh quote recorded, and refused with `LEG_TERMS_CHANGED` (intent
  `PARTIALLY_COMPLETED`, nothing built, no budget moved) when they cannot
  meet them. Submission requires every earlier batch finalized
  (`BATCH_NOT_READY`), evaluates policy once per leg with one reservation
  per leg keyed `<intent>:<transaction>[:<leg>]` (every hold released on a
  denial; the attempt settles them together), and plan expiry at build or
  submission ends the intent as `EXPIRED` or, after fills,
  `PARTIALLY_COMPLETED`. Status derives `batches` from fills, attempts and
  prepared rows (`pending`, `prepared`, `submitting`, `submitted`,
  `confirmed`, `finalized`, `failed`, `expired`, `cancelled`, `unknown`,
  `stale`) and answers `nextAction: review` for a partially completed
  basket. Cancel in `AUTHORIZED` after a fill ends `PARTIALLY_COMPLETED`
  with the prepared later transaction withdrawn; cleanup ordering is the
  guarded intent transition, then the prepared rows, then the outbox event.
- Reviewed completion: `POST /v1/me/intents` with `continuationOfIntentId`
  creates a basket investment for exactly the legs the named
  `PARTIALLY_COMPLETED` intent left unfilled: same wallet and version, a
  budget equal to the sum of their original targets (`VALIDATION_FAILED`
  names `walletId`, `strategyVersionId` or `budget.rawAmount`), once per
  original (`continuedByIntentId`, set in a guarded update). Its plan keeps
  the original targets (no re-weighting, no cash remainder, no second
  protocol-fee reserve), quotes and policy-checks them afresh and executes
  as any plan.
- `@markov/db`: migration `0012_continuations` (continuation columns on

  `liveAttemptRowsOf`; reservation settlement by attempt covers the per-leg
  keys; `markIntentContinued`. Config: `EXECUTION_VENUE_FIXTURE_COMPOSE_MAX_LEGS`.
- API routes, OpenAPI and `@markov/api-client` regenerated (matrix rows

## Unresolved risks and dependencies

- A live route (OD-21) is still the gate before any execution outside
  fixtures, and a live basket additionally needs a compose contract for
  the gateway (or a per-leg staged run, which the code already supports).
- Plan validity is the earliest quote expiry, so a staged run must finish
  within it; a later leg past validity ends the run `PARTIALLY_COMPLETED`
  by design. Whether validity should be per batch is a product decision.
- The refreshed quote of a later leg is checked against the approved
  bounds and recorded, but the prepared transaction still references the
  plan's approved quote in `legs[].quote`; the fresh quote lives in
  `venue_quotes` for the plan.
- Frozen legs are ordered by instrument id, so a basket's leg order (and
  therefore the order of a staged run) depends on the ids; the tests now
  assert order-independently. A weight-ordered execution order would be a
  planning change.
- Per-leg policy evaluations at submission declare the plan's other legs as
  exposure and reserve one leg at a time; for large baskets the account cap
  can be reached a leg earlier than at plan time, which is conservative,
  never permissive.
- The outbox now carries `execution.partial`; nothing publishes it until
  B18. The fixture chain's simulation at plan time uses the same state the
  build uses later, so a composition can pass at plan time and fail at
  build time when balances moved; that is a refusal, never a fallback.
