## Delivered

- **From approval to a signed submission.** The review's approval panel
  hands over to an execution panel (`features/execution/execution-panel.tsx`)
  that asks the API to build the plan's next transaction and shows it
  before the wallet opens: each leg's mint with the most it may spend and
  the least it must receive, the network cost at most (fee, priority, rent
  for created accounts) and the payer, the signer, the blockhash and its
  last valid block, the simulation result, the decoded instructions and
  the message hash. "Sign transaction k of N" stays unavailable with its
  reason until the pure model (`execution-model.ts`) finds every
  precondition true: the transaction belongs to this intent and to the
  plan whose hash was approved, the connected account is the plan's wallet
  on the app's cluster, the wallet can sign transactions, the plan has not
  expired, the unsigned bytes hash to the message the API validated (a
  written-out SHA-256, `sha256.ts`, so the check never depends on
  `crypto.subtle`), and the simulation passed. The wallet receives the
  exact prepared bytes through the F08 `signTransaction` path; the returned
  bytes must be the same message with the fee-payer slot filled and must
  hash to the same message (`transaction-check.ts`), or nothing is sent.
  One click is one wallet request and at most one submission of the
  signed bytes; the API verifies everything again before its one broadcast.
- **Wallet and submission outcomes without a second intent.** A declined
  signature keeps the built transaction and sends nothing; a silent wallet
  is called out after 45 s with "Stop waiting", after which a late
  signature is discarded; mutated bytes, a wallet, account or session
  changed while the popup was open, and a connected account that is not
  the plan's wallet refuse without submitting. API refusals (signature
  mismatch, expired plan or blockhash, policy denial, attempt in flight,
  batch not ready, leg terms changed) say what was and was not sent and
  leave the next real step. A lost HTTP answer after the bytes left the
  browser is treated as unknown: the existing attempt is reconciled from
  chain evidence and never re-signed. A node that gave no answer leaves
  the intent "Result unknown; reconciling" until the chain decides.
- **Timeline and transport.** `/activity/[intentId]` is the restorable
  execution record: per transaction the stages built → signed → broadcast
  → confirmed → finalized → fills recorded (done, now, pending, failed,
  unknown, skipped) with the node's confirmation and slot, resends, landed
  errors and expiries, the signature with an explorer link where the
  cluster has one, the fills from the landed transaction's balance changes
  with their bounds, the network fee actually paid, and the reconciliation
  evidence and last check. The backend has no event stream, so the
  transport is bounded polling of the status route (2 s while the network
  is watched, 5 s after 30 s, 15 s in a hidden tab, off when settled or
  when the person is the next actor), with backoff on failed reads and a
  "stale" label instead of a guess. State changes are announced through a
  polite live region, never every poll. A reload, a second tab and a
  closed popup come back to the same record.
- **Recovery.** Cancel before any signature (with the consequence: nothing
  sent, or "stop here" after earlier fills), a cancellation request after
  a broadcast (the signed transaction can still land), nothing once a
  transaction landed. A partially completed basket shows the filled leg
  and the stale or failed one with its reason and offers "Review the
  unfilled legs", a reviewed completion on the same review screen
  (`/review/new?continueIntentId=…`, budget equal to the unfilled targets,
  which the API checks). An expired transaction is built again; a frozen
  intent waits for a person and retries nothing.
- **Activity and receipts.** `/activity` lists the person's orders newest
  first with validated URL filters (open, in flight, needs attention,
  settled) and a stable deep link per row. Once every transaction
  finalized, "Issue a receipt" asks the API for the execution receipt and
  opens `/receipts/[receiptId]`: what was requested, approved, submitted,
  filled, charged and reconciled with timestamps and version references,
  the signing key with its published status, the canonical hash, the JSON
  to verify offline with `markov receipts verify`, and the public opt-in
  (redacted by the API). The page says what a receipt is and is not.
- **Design reference realignment.** Tokens follow the reference
  (periwinkle accent `#8299FD`, a separate `eyes` token `#578FFE` so the
  pixel eyes stay blue, bezel `#E6DCD1`, screen `#070909`, panels
  `#121416`) with the measured contrast table recomputed; the primary
  sections are Explore, Build, Portfolio and Activity, the eyes and
  wordmark lead home, and a chip names the real environment outside
  production. The reference's single-row top-bar link layout and its
  Explore and Set Rules tables remain for the sessions that own those
  screens (`docs/frontend/design-reference/README.md`).
- **Plumbing.** Proxy allowlist for the B10 to B12 execution, reconciliation,
  receipt, visibility, keys and public receipt routes (submission index 0
  to 31 only) with tests; TanStack queries and mutations; route registry;
  the review's simulation row now reads the plan-time simulation and the
  header knows single sells; the e2e API launcher enables execution writes
  and a throwaway receipt key for the fixture run.

## Provider verification status

No provider is involved beyond the fixture venue and the fixture chain of
B09 to B11, which exist on no network, and the local receipt signing key
of B12, which production refuses. Every signature was the fixture
wallet's over bytes the fixture venue built; nothing was sent to a live
cluster, no funds were spent, no mandate created, no message sent. Live
funded verification needs explicit authorization and approved caps
(OD-21) and a KMS-backed receipt key (OD-22).

## Unresolved risks and dependencies

- The transport is polling; the backend has no owner-authorized event
  stream. Stream reconnect, gap refetch and cursor semantics from the
  build prompt are represented by the polling schedule, backoff and the
  stale label, and belong to the session that adds the stream (B18 or the
  operations session).
- The wallet context signs legacy transactions only (F08); the contract
  allows `v0` and a gateway venue may build one. A wallet declaring only
  `0` is refused as unsupported before any bytes reach it.
- A user's rejection and any other wallet error both surface as
  "declined" (the Wallet Standard gives no code); the copy says nothing
  was sent either way.
- Receipt verification in the browser is the key's published status and
  the JSON for the CLI; cryptographic verification in the app needs a
  frontend-safe canonical JSON and Ed25519 (WebCrypto) and arrives with
  F11's receipt detail and export.
- The fee actually charged by a transaction that landed with an error is
  not carried by the execution status (fills exist only for landed
  successes); the timeline says so instead of showing zero.
- Single sells are not started from the app yet (the instrument page's
  Sell stays unavailable); the review and the timeline already read
  `single_sell` intents created through the CLI.
- The reference's top-bar link row and tables (Explore Strategies, Set
  Rules) are not applied; the rail and bottom bar remain until the shell
  pass.
