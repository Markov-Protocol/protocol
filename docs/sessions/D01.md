## Design notes

- The site is a build product of the repository, so a document, a route
  or a command cannot drift from the site without a build failing or the
  page changing; "the documentation works as the reference for the actual
  working" holds because the reference pages are generated from the
  contract the API exports and the program the CLI runs, and the guides
  quote the startup check that CI executes.
- Generated pages are not committed: the diff of a change stays in the
  source document, the route or the command, and the site follows.
- `readme.md` files under a synced folder become the folder's index page
  (`/docs/reference/frontend`, `/docs/reference/frontend/design-reference`),
  which is Docusaurus's category-index convention.
- The docs app has no `"type": "module"`: webpack treats `.js` under an
  ESM package as strict ESM and Docusaurus's server bundle then fails with
  `require.resolveWeak is not a function`; the scripts are `.mjs` files
  and unaffected.
- Dark is the default regardless of the OS preference
  (`respectPrefersColorScheme: false`): the Mark I screen is the product's
  identity, and the toggle remains for anyone who prefers the light
  screen. The dark variables are declared on `html[data-theme="dark"]`
  because the theme's own declaration has that specificity.
- The site never claims a deployment: OD-24 records that hosting the
  built output under `markov.pet/docs` is a deployment decision outside
  this repository; no session deploys it.

## Verification

The first browser runs failed on three of my own assumptions rather than
on the site: the local search renders its results in a `role="listbox"`
without the class names I had guessed (the site's search worked from the
first build; the assertion now reads the listbox); a Docusaurus category
without a link is a button, not a link, and the phone drawer opens on the
docs sidebar so the navbar items are one "Back to main menu" up; and the
dark screen was Infima's default grey because the theme declares its
dark variables on `html[data-theme="dark"]`, one specificity level above
mine (the test caught it: `rgb(27, 27, 29)` instead of `rgb(7, 9, 9)`).
With those fixed, every check passed at both widths, and the screenshots
show the cream perimeter with the dark screen (`docs-home-dark-*.png`),
the light screen after the toggle (`docs-home-light-*.png`), the API
reference, the CLI reference and the methodology page.

The full gate ran green with the site included: `pnpm verify` ends with
`pnpm docs:build`, which syncs 64 repository documents, generates 135 API
operations and 20 CLI command groups and builds with broken links and
anchors as errors; `pnpm typecheck` includes the docs app; the new CI
steps build the site and run the browser checks after the web evidence.
The browser checks ran against the build that `pnpm verify` produced. The
lockfile installs frozen. The docs site itself was not deployed; the
evidence is the served local build.

## Unresolved risks and dependencies

- Hosting (OD-24): the static host for `apps/docs/build` under the
  `/docs/` prefix, the publish job on `main` and the review step are not
  chosen; until then the site exists in every CI run and in local
  previews only.
- The search index is built from every page, including the session logs
  and the generated references (about 4.7 MB); it loads on the first
  focus of the search box. If it grows further, restrict the indexed
  paths or split the index by section.
- The generated API reference renders schemas to a depth of three and
  lists `anyOf` variants; a deeper or recursive schema shows as `object`
  with a link to the OpenAPI document. The CLI reference lists commands,
  arguments and options; command behaviour is documented in the guides
  and the backend contract, not extracted from code.
- The site reads Inter and the design tokens from the app and the UI
  package by relative path; moving those files breaks the docs build
  (which is the intended coupling).
