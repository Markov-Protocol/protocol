## Design notes

- The scheduler creates proposals and notifications, never transactions.
  The authority path is the same as for an agent: the schedule principal
  cannot open, the worker credential can only ask for passes, an operator
  can run a pass but cannot open, and the owner's session opens a
  proposal into an intent that still needs a plan, an acknowledgement and
  a signature. `automation.unattended` stays `DISABLED`; the mandate dry
  run defines the interface and stores nothing.
- Durability is split as the specification asks: Temporal keeps the loop
  alive across worker restarts and holds no database or authority; the
  database keeps side effects idempotent (one schedule per transaction,
  occurrences unique per sequence, proposals unique per dedup key). A
  pass repeated after a crash between the proposal insert and the
  occurrence commit answers the existing proposal.
- Missed occurrences default to `skip`: a schedule that was paused, or a
  worker that was down, never turns several missed budgets into several
  proposals at once; `catch_up_latest` proposes exactly one.
- Notifications are projected from the existing `mark_events` log rather
  than emitted a second time, so every fact has one source and a rerun
  projects nothing twice. Email is opt-in per category after a verified
  address, off by default except `security`, and every message carries an
  app path only.
- Rebalance legs are sized from the attributed holdings and reference
  prices at proposal time; opening creates ordinary intents, sells first,
  so every leg is reviewed and signed separately and a proposal for an
  empty instance is a report with no legs.
- The `notifications.id` column is a unique constraint rather than an
  index: a foreign key from deliveries needs the constraint, and the
  first migration draft failed on that in the test database.

Fixes made while testing, all covered by the final runs:

- The first `0017_maintenance` migration failed in the test database:
  the foreign key from `notification_deliveries` referenced
  `notifications.id`, which was a unique index created after the
  constraint. The column is now a unique constraint inside the table and
  the migration was regenerated.
- The drift scenario used a 24-hour review window, so the day-two check
  found the first proposal expired and proposed again (correct behaviour,
  wrong scenario); the test now uses a 48-hour window and shows the
  `open_proposal_exists` skip, then a new proposal after the owner opened
  the first and the interval passed.
- The fixture provider's failure predicate matched the subject text,
  which a strategy-draft proposal's title does not contain; it now fails
  every notification message by its idempotency key and lets
  verification messages through.
- Notification bodies attributed a proposal the owner made through the
  tool API to "the companion"; the origin is now derived from the
  creator (schedule, agent credential, companion run or the owner).

## Unresolved risks and dependencies

- An email provider (OD-25): sender domain, terms, retention, bounce and
  complaint handling and whether webhooks feed delivery state must be
  recorded before `NOTIFICATIONS_EMAIL_PROVIDER=configured` is set
  anywhere but a local gateway.
- Drift is measured at pass time from the journal and the reference
  prices; a stale or missing observation makes the allocation incomplete
  and the occurrence `target_unavailable` rather than a wrong proposal,
  so a live price source (OD-23) also decides how often drift schedules
  produce anything.
- The pass runs in the API request of the worker's tick with a bounded
  batch; many schedules due at the same minute are spread over
  successive ticks. A per-owner throttle beyond the batch bound and a
  per-provider throttle for email are not implemented.
- Rebalance legs are sized from attributed holdings; wallet-level
  remainders (lots not attributed to the instance) are not sold, and a
  leg smaller than the dust threshold is dropped.
- The worker credential is a bearer token in the worker's environment;
  rotation is manual (`markov workers create`, then replace
  `MAINTENANCE_API_TOKEN`) and the old credential expires on its own.
- The app's automations and notification screens are F13.
